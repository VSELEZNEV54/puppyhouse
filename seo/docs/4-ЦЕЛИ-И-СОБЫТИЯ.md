# Цели и события: что заводить сразу

Цель в Метрике — это не «настройка», а **определение того, что считается
успехом**. Пока цели нет в кабинете, событие из кода не считается вообще:
Метрика его молча выбрасывает.

Главное правило, из которого растут все остальные:

> **Идентификатор цели в кабинете должен совпадать с именем в коде
> посимвольно.** Расхождение в одном символе — цель не сработает никогда, и
> узнать об этом нечем: ошибки не будет, в отчёте просто ноль.

Поэтому источник правды — **один файл**: `seo/project.json`, ключ `goals`.
Оттуда список читает `goals.mjs`, когда заводит цели в счётчике. Если в
проекте есть тесты, стоит добавить проверку, что каждая цель из списка
отправляется кодом и каждая отправляемая есть в списке (у нас это
`test_frontend_sends_every_goal`).

## 1. Базовый набор — годится любому сайту

Девять целей, которые имеет смысл завести сразу, ещё до того как вы
придумаете продуктовые. Пять из них в перенесённом коде **уже автоматические**
и не требуют правок в страницах.

| Идентификатор | Название в кабинете | Когда | Автоматическая |
|---|---|---|---|
| `lead_submit` | Заявка отправлена | успешный ответ сервера на отправку формы | нет |
| `lead_fail` | Заявка не ушла (сбой) | сервер ответил ошибкой | нет |
| `contact_click` | Клик по контакту | клик по `mailto:` или ссылке на Telegram | **да** |
| `lead_subscribe` | Подписка на обновления | форма подписки (обычно в подвале) | нет |
| `blog_read` | Дочитал статью | прокрутка ≥75% **и** ≥60 с на странице | **да** |
| `blog_cta_click` | Клик по кнопке в блоге | CTA внутри статьи | **да** |
| `consent_full` | Согласие: всё, включая Вебвизор | кнопка «Принять все» | **да** |
| `consent_stats` | Согласие: только статистика | кнопка «Только статистика» | **да** |
| `demo_view` | Открыл демо | заход на страницу демо/примера | **да** |

**Зачем `lead_fail`.** Форма, которая молча не отправляется, — самая дорогая
поломка на сайте: трафик идёт, заявок нет, и выглядит это как «плохой
трафик». Отдельная цель на сбой показывает такое сразу.

**Зачем цели про согласие.** Метрика не видит тех, кто отказался: они не
попадают в статистику вообще. Соотношение `consent_full` к `consent_stats`
показывает, какой доле визитов доступен Вебвизор, и помогает понять,
насколько полна сама статистика. Это единственный способ оценить размер
слепой зоны, которую создаёт строгая модель согласия.

**Почему `blog_read` требует И глубины, И времени.** Прокрутка без времени —
это пролистывание до конца за три секунды. Время без прокрутки — открытая и
брошенная вкладка. Поодиночке каждое условие врёт.

**Чего в базовом наборе нет намеренно:** «просмотр страницы N секунд»,
«скролл 25/50/75%», «клик по любой кнопке». Такие цели дают красивую
конверсию и ноль решений: по ним нельзя понять, что менять.

## 2. Продуктовые цели: пример воронки «проверка → оплата»

Так выглядит рабочий набор проекта, с которого снят пакет. Переносите не
список, а **принцип**: один шаг воронки — одна цель, и шагов столько, сколько
реально есть у человека на пути к деньгам.

### Деньги

| Идентификатор | Название | Когда срабатывает |
|---|---|---|
| `scan_start` | Запустил проверку сайта | нажал главную кнопку, ввод корректен |
| `scan_done` | Увидел отчёт | результат отрисован |
| `scan_error` | Проверка не удалась | таймаут, недоступный сайт, ошибка сервера |
| `pay_modal_open` | Открыл окно оплаты | клик по «Разблокировать» |
| `pay_start` | Ушёл на оплату | платёж создан, переход в платёжную систему |
| `purchase` | Оплатил (вернулся на сайт) | вернулся с оплаты, доступ открыт |
| `purchase_confirmed` | Оплата подтверждена (сервер) | досылает бэкенд по ClientID — **все** оплаты |

### Заявки

| Идентификатор | Название | Когда срабатывает |
|---|---|---|
| `lead_free_report` | Заявка: отчёт на почту | оставил email в попапе |
| `lead_consult` | Заявка: консультация | форма консультации |
| `lead_blog` | Заявка: из блога | форма внутри статьи |
| `lead_package` | Заявка: пакет документов | форма продукта |

### Качество трафика

`blog_read`, `blog_cta_click`, `demo_view`, `consent_full`, `consent_stats`,
`contact_click` — из базового набора.

## 3. Две цели про оплату: самое важное место

Если на сайте есть деньги, их считают **двумя** целями, и это не дублирование:

* **`purchase`** — фронтовая. Срабатывает, только если плательщик вернулся на
  сайт. Сигнал мгновенный → годится для оптимизации рекламы.
* **`purchase_confirmed`** — серверная, офлайн-конверсией по ClientID.
  Покрывает **100% оплат**, но с задержкой обработки до нескольких часов.

> **Не складывайте их.** `purchase` — подмножество `purchase_confirmed`.
> Реальное число оплат — всегда `purchase_confirmed`.

Отсюда же правило для «ключевых целей» в кабинете: ключевой делайте
`purchase_confirmed`, иначе Метрика будет оптимизировать и сравнивать по
неполным данным.

## 4. Воронка (составная цель)

Когда цели заведены, добавьте **составную цель**: Метрика нарисует по ней
воронку и сразу покажет, на каком шаге теряются люди. Задаётся в
`seo/project.json` (`funnel`) и создаётся командой `goals.mjs setup`.

```
scan_start → scan_done → pay_modal_open → pay_start → purchase_confirmed
```

Правила, которые стоит соблюдать:

* шаги — только те цели, которые человек проходит **по порядку**;
* последним шагом — деньги, и именно серверная цель;
* 4–6 шагов. Воронка из десяти шагов не читается, а каждый лишний шаг
  добавляет свою долю потерь и размывает картину.

## 5. Настройки счётчика, без которых цели врут

`goals.mjs setup` делает их одной командой; знать, зачем они, всё равно надо.

### 5.1. Электронная коммерция

Контейнер данных — `dataLayer` (ровно тот, куда пишет `metrika-goals.js`).
Без этой настройки покупка уходит в пустоту, и отчёта «доход по каналам
трафика» не будет.

### 5.2. Обрезка GET-параметров

Список параметров, которые Метрика игнорирует при склейке адресов:

```
id  token  paid  url  mode  pages
```

Зачем: без этого отчёт «Страницы» разваливается на тысячи уникальных адресов
вида `/result?id=<uuid>` и `/checking?url=…`. После настройки они схлопываются
в `/result` и `/checking`, и отчёт становится читаемым. Ссылки в Вебвизоре при
этом не теряются: там виден полный адрес визита.

Добавляйте в список **свои** технические параметры — любые, которые делают
один и тот же экран разными адресами.

## 6. Как называть цели

| Правило | Плохо | Хорошо |
|---|---|---|
| латиница, нижний регистр, подчёркивание | `ЗаявкаОтправлена` | `lead_submit` |
| префикс по смыслу, а не по месту на странице | `button_header_click` | `lead_consult` |
| название в кабинете — по-русски, человеку | `lead_blog` | «Заявка: из блога» |
| уточнения — параметрами, а не новыми целями | `contact_click_tg`, `contact_click_mail` | `contact_click` + `{channel: 'telegram'}` |

Про последнее: параметры цели видны в отчёте отдельной разбивкой, и это лучше,
чем плодить цели. Пять целей на один клик по контакту засоряют список и
мешают выбрать ключевые.

---

## 7. Как завести цель руками (запасной путь)

Если CLI почему-то недоступен: Настройка → Цели → Добавить цель → тип
**JavaScript-событие** → в поле «Идентификатор цели» вставить значение из
первой колонки, в «Название» — текст из второй.

Новую цель нужно **обязательно** добавить и в `seo/project.json`, иначе
инструмент о ней не знает, а проверка согласованности со временем начнёт
врать.

И помните: **Метрика не проверяет дубли**. Повторное создание цели с тем же
условием даёт вторую цель и ответ 200 OK. Удалить цель через API нельзя.
Поэтому `goals.mjs` всегда сверяется с тем, что уже есть, — и руками стоит
делать то же самое.
