# Методология: как устроена аналитика и почему именно так

Документ объясняет связку целиком: что происходит с момента, когда посетитель
открыл страницу, и до момента, когда владелец видит цифру в отчёте или строку
в Telegram. Читается до того, как начнёте что-то переносить: половина решений
здесь неочевидна, и без причин их легко «упростить» обратно в поломку.

---

## 1. Схема: фронт → события → цели → бэкенд → отчёты

```
   ПОСЕТИТЕЛЬ ОТКРЫЛ СТРАНИЦУ
            │
            ▼
   ┌──────────────────────────────────────────────┐
   │  cookie-banner.js — ЭКРАН СОГЛАСИЯ           │   до выбора НЕ ГРУЗИТСЯ
   │  три кнопки: всё / только статистика / нет   │   ни один трекер
   └──────────────────────────────────────────────┘
       │                      │
       │ localStorage         │ события в window:
       │ ['..._consent']      │  :consent-full / :consent-stats / :consent-denied
       │ = full|stats|denied  │  :consent-choice  (только НА КЛИК)
       ▼                      ▼
   ┌──────────────────────────────────────────────┐
   │  yandex-metrika.js — СЧЁТЧИК                 │
   │  full  → tag.js + init{webvisor:true}        │
   │  stats → tag.js + init{webvisor:false}       │
   │  denied/нет выбора → не грузится вообще      │
   └──────────────────────────────────────────────┘
            │ window.ym готов
            ▼
   ┌──────────────────────────────────────────────┐        ┌────────────────┐
   │  metrika-goals.js — ЦЕЛИ                     │        │  attribution.js│
   │  svpGoal / svpGoalThen / svpGoalOnce         │        │  first-touch:  │
   │  + автоцели (контакт, дочитывание, CTA)      │        │  utm, referrer,│
   │  + ecommerce в dataLayer                     │        │  landing, yclid│
   │  очередь: цель раньше счётчика — не теряем   │        │  + ClientID    │
   │  sessionStorage: цель переживает ПЕРЕХОД     │        │  (после согл.) │
   └──────────────────────────────────────────────┘        └────────────────┘
            │ reachGoal                                        │ window.svpAttribution()
            ▼                                                  ▼
   ╔══════════════════════╗                        ┌──────────────────────────┐
   ║   ЯНДЕКС.МЕТРИКА     ║                        │  ФОРМА отправляет POST   │
   ║   цели, визиты,      ║                        │  { …, attribution: {…} } │
   ║   Вебвизор, деньги   ║                        └──────────────────────────┘
   ╚══════════════════════╝                                   │
            ▲                                                 ▼
            │                              ┌──────────────────────────────────┐
            │  офлайн-конверсия            │  БЭКЕНД                          │
            │  purchase_confirmed          │  sanitize_attribution → JSONB    │
            │  (ClientID, цена, время)     │  classify_source → «🔍 Поиск»    │
            │                              │  → Telegram владельцу + админка  │
   ┌────────────────────────┐              │  оплата подтверждена →           │
   │  metrika_service.py    │◄─────────────│  задача metrika.offline_conversion│
   │  + задача Celery       │              └──────────────────────────────────┘
   └────────────────────────┘
            │
            ▼
   ╔════════════════════════════════════════════════════════════════════╗
   ║  ОТЧЁТЫ — командная строка seo/ (кабинет не нужен)                 ║
   ║  doctor.mjs     живы ли доступы                                    ║
   ║  metrika.mjs    трафик, страницы входа, достижения целей           ║
   ║  webmaster.mjs  запросы, показы, позиции, что выпало из поиска     ║
   ║  gsc.mjs        то же со стороны Google                            ║
   ║  goals.mjs      создать цели и настройки счётчика через API        ║
   ╚════════════════════════════════════════════════════════════════════╝
```

Ключевое свойство схемы: **согласие — единственная точка входа**. Нет выбора
посетителя — нет ни счётчика, ни целей, ни ClientID. Всё остальное построено
так, чтобы это не приводило к потере данных там, где их можно сохранить
законно (метки перехода, факт оплаты на сервере).

## 2. Четыре файла фронта и почему их четыре, а не один

Файлы разделены по обязанностям, и это не вкусовщина: каждый меняется по
своему поводу и своим ритмом.

| Файл | Единственная обязанность | Меняется, когда |
|---|---|---|
| `cookie-banner.js` | спросить согласие и объявить его результат | меняются тексты, дизайн, юридическая модель |
| `yandex-metrika.js` | загрузить счётчик ровно тогда, когда согласие есть | меняются опции счётчика (Вебвизор, карта кликов) |
| `metrika-goals.js` | что мы считаем конверсией и как это надёжно отправить | появляются новые кнопки, формы, продукты |
| `attribution.js` | запомнить, откуда человек пришёл впервые | появляются новые рекламные click-id |

Связь между ними — не вызовы функций, а **события в `window` и ключ в
`localStorage`**. Поэтому порядок подключения скриптов не критичен: счётчик
и читает сохранённый выбор при старте, и слушает событие на случай, если
выбор сделан кликом в этой же сессии. На разных страницах порядок
`defer`-скриптов оказывается разным — связка это переживает.

## 3. Принятые решения и их цена

Каждое из этих решений однажды уже обсуждалось и однажды уже оплачено.
Если будете менять — меняйте зная цену.

### 3.1. Аналитика только после согласия (строгая модель 152-ФЗ)

**Решение.** Никакой трекер не загружается до явного клика в экране согласия.
Не «баннер показали и грузим», не «грузим, а по отказу выключаем» — именно
не грузится.

**Цена, принятая владельцем сознательно.** Кабинет Метрики показывает
**меньше визитов, чем есть на самом деле**. Отказавшиеся и не выбравшие
ничего не попадают в статистику вообще: ни визита, ни источника, ни цели.
Отчёты занижены, и сравнивать их с чужими «полными» цифрами бессмысленно.

Так и задумано: это не баг, не повод «вернуть как у всех» и не дефект
настройки. Отдельные цели `consent_full` и `consent_stats` существуют ровно
для того, чтобы видеть масштаб этой платы — какой доле визитов вообще доступен
Вебвизор.

**Что из этого следует для продукта.** Факт оплаты нельзя оставлять только на
фронте: у отказавшегося нет ClientID, и его деньги в аналитику не попадут
никогда. Поэтому деньги считаются на сервере, а в Метрику досылаются отдельной
целью (п. 3.5).

### 3.2. Метки перехода храним без согласия, ClientID — только с согласием

**Решение.** `utm_*`, `yclid`, `gclid`, `referrer` и страница входа
сохраняются в `localStorage` сразу, до любого согласия. ClientID Метрики
дописывается отдельным слоем и только после того, как счётчик поднялся,
то есть после согласия.

**Почему так.** utm-метки — параметры самого перехода, которые посетитель
принёс в адресной строке; это не трекер третьей стороны и не идентификатор
пользователя. ClientID — идентификатор, его собирает Метрика, и он требует
согласия. Разделение позволяет знать источник заявки даже у того, кто от
аналитики отказался.

**Цена.** У части заявок источник известен, а пути по сайту (Вебвизора) нет.
В уведомлении это видно: источник есть, ClientID пуст.

### 3.3. First-touch, а не last-touch

**Решение.** Источник фиксируется при **первом** заходе и не перезаписывается
90 дней.

**Почему.** Владельцу важно, **где человек узнал о продукте**, а не с какой
вкладки он вернулся дооформить заявку. Last-touch в такой модели всегда
показывает «прямой заход» и «поиск по бренду» — красиво и бесполезно.

**Цена.** Человек, пришедший в июне из статьи и купивший в сентябре по
рекламе, будет записан статье. Для оценки рекламы это неудобно; для оценки
контента — правильно. Если понадобится и то и другое, второй слой атрибуции
добавляется, но первый трогать нельзя.

### 3.4. Цели не теряются: очередь в памяти + очередь, переживающая переход

**Решение.** `svpGoal` не отправляет цель, если счётчика ещё нет, а ставит её
в очередь и досылает, как только `window.ym` появится (ждёт до 20 секунд).
`svpGoalThen` для случая «цель и сразу уходим со страницы» кладёт цель в
`sessionStorage`, и её досылает уже следующая страница (TTL 10 минут).

**Почему.** При строгом согласии счётчик поднимается позже, чем человек
начинает действовать. Классическая картина: человек жмёт «Принять все» и
тут же нажимает главную кнопку — `tag.js` в этот момент ещё грузится.
А если кнопка ведёт на другую страницу, браузер уносит очередь в памяти
с собой.

**Чем это было оплачено.** Главная цель воронки («запустил проверку»)
считалась 8 раз при 447 реальных запусках: цель отправлялась на главной, где
счётчика ещё не было, и терялась на переходе. Это не теория, это был
полностью слепой верх воронки. Подробно — в [5-ГРАБЛИ.md](5-ГРАБЛИ.md).

### 3.5. Две цели про оплату, и их нельзя складывать

**Решение.**

* `purchase` — отправляет фронт, когда плательщик вернулся на сайт;
* `purchase_confirmed` — досылает сервер по ClientID, по **каждой**
  подтверждённой оплате.

**Почему две.** Фронтовая цель быстрая (годится для оптимизации рекламы в
реальном времени), но видит только вернувшихся — а возвращаются далеко не все:
закрыл вкладку, платил с телефона, ушёл читать письмо. Серверная цель полная,
но приходит с задержкой до нескольких часов (так работает загрузка офлайн-
конверсий у Яндекса).

**Цена и главный риск чтения отчётов.** `purchase` — подмножество
`purchase_confirmed`. **Складывать их нельзя**, иначе выручка удвоится.
Реальное число оплат — всегда `purchase_confirmed`.

**Ограничение API, о котором надо знать заранее:** конверсия применяется к
визитам не старше **21 дня**. Просроченное не догнать никогда, поэтому у
задачи есть повторы и часовой добор по расписанию с окном 20 дней.

### 3.6. Вебвизор включается только при инициализации счётчика

**Решение.** Уровень согласия `full` → счётчик поднимается с
`webvisor: true`; `stats` → с `webvisor: false`.

**Почему так, а не «включим по клику».** У Метрики нет публичного метода
включить запись действий на лету. Поэтому: согласие было дано раньше —
запись идёт с первой же страницы; согласие дано кликом в этой сессии —
запись начнётся со следующего перехода, когда счётчик инициализируется заново.

**Цена.** Первая страница визита у только что согласившегося в Вебвизор не
попадает. Пытаться это обойти — значит грузить счётчик до согласия, то есть
отменить п. 3.1.

### 3.7. Источник лида считает сервер, а не фронт

**Решение.** Фронт присылает сырые данные (`referrer`, метки, страница
входа, ClientID), сервер их нормализует (`sanitize_attribution`) и
классифицирует (`classify_source`) в человекочитаемую метку: «🔍 Поиск —
Яндекс», «💰 Реклама», «📣 Соцсети — Telegram».

**Почему.** Это данные от клиента — то есть недоверенные: их можно подделать
или прислать мусор, которым раздувается JSONB-колонка. Нормализация на входе
берёт только известные поля с обрезкой длины. Классификация же меняется чаще
кода форм (появилась новая соцсеть — поправили один словарь), и держать её в
одном месте дешевле, чем в десяти формах.

**Побочная выгода.** `classify_source` — чистая функция без БД и сети:
проверяется тестами мгновенно и переносится в любой проект как есть.

### 3.8. Инструменты без зависимостей, вместо готовых библиотек и MCP-серверов

**Решение.** `seo/` — свой код на Node 18+: `fetch` встроенный, подпись ключа
Google делается встроенным `node:crypto`. Ни одной внешней зависимости.
Сторонние MCP-серверы для Метрики и Вебмастера не подключаем.

**Почему.** Чтобы работать, инструменту нужен токен с правом **менять
настройки сайта** и (при подключённом Директе) тратить рекламный бюджет.
Сторонние серверы — это чаще всего репозитории без аудита, которые при каждом
запуске подтягивают свежую версию: чужой код обновляется без вашего ведома,
имея ваши ключи. Своих тут 300 строк на сервис, они лежат в вашем git и ходят
только в официальные API.

**Цена.** Часть удобств приходится писать самому, и форматы ответов API
выясняются по живым ответам, а не по документации (в документации Яндекса
встречаются устаревшие и просто неверные места — см. грабли).

### 3.9. Чего не подключаем намеренно

| | Почему нет |
|---|---|
| **Google Analytics 4** | Для российского сайта Метрика даёт больше (Вебвизор, карта скроллинга, фразы Яндекса). GA обрабатывает данные за рубежом — это трансграничная передача персональных данных с отдельной ответственностью. Выигрыш — срез Google-трафика, который и так виден в Search Console. |
| **Google Indexing API** | Официально обслуживает только страницы с разметкой вакансий и трансляций. Статьи он примет с кодом 200 и молча проигнорирует. Статьи, подающие это как лайфхак, врут. |
| **Парсеры Вордстата** | Нарушают правила Яндекса. Частотности через API Директа получить нельзя вообще: в пятой версии нет метода, возвращающего число показов. Спрос измеряем Вебмастером — по своим показам. |
| **Сторонние MCP-серверы** | См. п. 3.8. |

## 4. На какие вопросы связка отвечает

Проверка смысла: если после развёртывания на эти вопросы ответа нет —
что-то не доделано.

| Вопрос владельца | Чем отвечается |
|---|---|
| Сколько людей дошло от входа до оплаты и где теряются? | составная цель (воронка) в Метрике |
| Сколько денег принёс поиск, а сколько реклама? | `purchase_confirmed` + e-commerce по каналам |
| Откуда пришёл человек, который прямо сейчас оставил заявку? | строка «Источник» в Telegram-уведомлении |
| Какие запросы приводят людей и на какие страницы? | `webmaster.mjs queries` / `monitoring`, `gsc.mjs` |
| Какие статьи читают, а какие открывают и закрывают? | цель `blog_read` (глубина ≥75% И время ≥60 с) |
| Статистика вообще полная? | соотношение `consent_full` / `consent_stats` |
| Доступы живы или токен протух? | `doctor.mjs` — отличает «не подключено» от «отвалилось» |

## 5. Что переносится, а что пишется заново

**Переносится как есть** (логика не зависит от продукта):

* механизм согласия и загрузки счётчика;
* ядро целей: очередь, отложенные цели, `svpGoal*`;
* first-touch атрибуция и её нормализация на сервере;
* офлайн-конверсии: сервис, задача, повторы, добор;
* все инструменты `seo/`.

**Пишется заново под новый проект:**

* тексты и оформление экрана согласия, ссылки на свои политики;
* список целей — он описывает ваш продукт, а не наш
  (базовый набор, годный любому сайту, — в [4-ЦЕЛИ-И-СОБЫТИЯ.md](4-ЦЕЛИ-И-СОБЫТИЯ.md));
* места вызова `svpGoal(...)` в кнопках и формах;
* словари «где оставлена заявка» и свои домены в классификаторе источника;
* товар в `ecommercePurchase`, если продаёте не отчёт.
