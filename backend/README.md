# Бэкенд домщенков.рф

Принимает заявки со всех форм сайта, отзывы и события на сайте. Складывает всё в одну базу PostgreSQL, где у каждой породы
есть своя «база» — представление. Показывает заявки в своей админ-панели (`/admin/`) и отдаёт их через API любой CRM.

```
сайт (статический, nginx) ──POST /api/v1/leads, /reviews, /events──▶ API (FastAPI) ──▶ PostgreSQL 16
                                                                      │                  ▲
                                         Telegram / почта / вебхук ◀── worker ───────────┘
админ-панель /admin/ ──Bearer-токен──▶ /api/v1/admin/… ◀── внешняя CRM (API-ключ)
```

## Как устроены базы

Одна база данных, одна общая таблица заявок `leads`: каждая заявка с каждой формы. Базы по породам — SQL-представления
с понятными колонками. Они пересоздаются автоматически, когда в `src/data/breeds.json` появляется порода.

| Представление | Что в нём |
|---|---|
| `leads_all` | все заявки — «одна большая база» (с названием породы) |
| `leads_maltipu`, `leads_buldog`, `leads_pudel`, `leads_kolli` | заявки одной породы (по `key` из breeds.json) |
| `leads_general` | заявки без породы («Пока не решил(а)», общие формы) |

Почему не отдельные физические базы на каждую породу: один человек часто спрашивает про две породы. Отдельные базы
разорвали бы его историю, не дали бы общей статистики, а удаление данных по 152-ФЗ пришлось бы делать в каждой базе.
Представления дают тот же раздельный вид без копий данных. В API то же самое — фильтр `?breed=maltipu`.

Остальные таблицы:

| Таблица | Зачем |
|---|---|
| `contacts` | человек; склейка по телефону (+7XXXXXXXXXX); `contact_aliases` — старые номера после ручной склейки |
| `lead_history` | лента заявки: создание, повторные запросы, статусы, ответственный, комментарии |
| `consents`, `consent_versions` | доказательство согласия (152-ФЗ): какой текст, когда, с какой страницы, IP |
| `visitors`, `sessions`, `site_events` | анонимные посещения: просмотры, открытия форм, клики по телефону и мессенджерам, тест породы |
| `reviews` | отзывы на модерации (публикуются только «Анна К.», город, порода, оценка, текст) |
| `breeds`, `puppies` | каталог; синхронизируется из `src/data/*.json` (сайт — источник истины) |
| `outbox` | очередь уведомлений менеджерам с повторами |
| `admin_users`, `admin_tokens` | менеджеры, сессии входа, API-ключи админ-панели |
| `audit_log`, `erasure_log` | кто что выгружал и удалял; акты уничтожения ПД (хранятся 3 года) |

### Что происходит с заявкой

1. Форма отправляет JSON на `POST /api/v1/leads`. Ошибку (422) вызывают только имя, телефон, «куда написать» и согласие.
   Неизвестный щенок, окрас или вид формы не теряют заявку: сырое значение сохраняется рядом.
2. Контакт находится или создаётся по телефону атомарно. Две параллельные заявки одного человека не создают двух контактов.
3. Если у человека уже есть открытая заявка той же породы (30 дней), новая становится «повторным запросом» к ней
   (`parent_id`, статус `duplicate`). Менеджер ведёт одну карточку на человека и породу.
4. Сохраняются согласие, источник (utm → yclid/gclid → поисковик/соцсеть → прямой заход), страница, связь с посещениями.
5. В той же транзакции ставятся уведомления. Воркер отправляет их и повторяет при сбоях.
6. Повторная отправка той же заявки (обрыв сети, двойной клик) распознаётся по `idempotency_key` и не создаёт дубля.

Защита от спама: скрытое поле-ловушка (`hp_note`), признаки «слишком быстро», «много с одного IP», «много с одного
номера» (такие заявки не теряются, а помечаются в `flags`), лимиты nginx, проверка `Origin`, только `application/json`.

## Запуск для разработки

```bash
cd backend
python3.13 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
createdb domshchenkov                     # PostgreSQL 16; URL по умолчанию — postgresql+psycopg://dsh:dsh@localhost:5432/domshchenkov
export DSH_DATABASE_URL=postgresql+psycopg://USER:PASS@localhost:5432/domshchenkov
python -m app migrate                     # схема + тексты согласий + каталог + представления
python -m app create-admin --login anna --name "Анна" --role admin
uvicorn app.main:app --reload             # панель http://127.0.0.1:8000/admin/, схема API /api/v1/docs
python -m pytest -q                       # тесты создают свою временную базу (нужно право CREATEDB)
```

Сайт отправляет заявки в API только на боевом домене: адрес задан в `src/data/site.json → api` (`origins`). На GitHub Pages
формы работают как прототип и ничего не отправляют. Для локальной проверки с настоящим API выполните в консоли браузера:
`localStorage['dsh:api'] = 'http://127.0.0.1:8000/api/v1'`. Сам API должен разрешать этот origin в `DSH_CORS_ORIGINS`.

## Продакшен

Пошаговая инструкция для владельца — [`DEPLOY.md`](../DEPLOY.md) в корне репозитория. Коротко:

```bash
git clone -b <ветка> https://github.com/VSELEZNEV54/puppyhouse.git /opt/domshchenkov/src
/opt/domshchenkov/src/backend/deploy/server-setup.sh --email you@example.ru   # один раз
/opt/domshchenkov/src/backend/deploy/deploy.sh                               # каждая выкладка (или: dsh update)
dsh app create-admin --login anna --name "Анна" --role admin
```

Сервер должен быть в России: это требование 152-ФЗ к хранению персональных данных граждан РФ. Подойдут Yandex Cloud,
Selectel, Timeweb, VK Cloud и т. п.

| Скрипт | Что делает |
|---|---|
| `deploy/server-setup.sh` | один раз: Docker (+ зеркала Docker Hub, ротация логов), nginx, certbot (webroot), ufw, fail2ban, swap, секреты в `/etc/domshchenkov/{db,api,backup}.env`, ключ age для бэкапов, cron. Повторный запуск ничего не перезаписывает |
| `deploy/deploy.sh` | из git-копии собирает релиз (`tools/release.sh`) и выкладывает: образ API с тегом версии, миграции, проверка `/health` (сломанный API → автоматический откат), сайт в `/var/www/domshchenkov`, nginx (`nginx -t`, иначе прежний конфиг), проверки через nginx. Отказывается при `[заглушках]` в согласиях и политике (`--allow-placeholders` — тестовый запуск) |
| `deploy/dsh` | `/usr/local/bin/dsh`: `status`, `logs`, `app …` (CLI бэкенда), `restart`, `backup`, `update`, `rollback` |
| `tools/release.sh` | релиз-папка и архив: собранный сайт (`site/` с 404.html, robots.txt, sitemap.xml) + `backend/` + `src/data` |
| `tools/check_launch.py` | что ещё заглушка: обязательное по 152-ФЗ, контакты, контент |

- `migrate` запускается при каждом деплое. Он применяет миграции, загружает новые версии текстов согласия и синхронизирует
  каталог щенков из `src/data`. После обновления `puppies.json` выложите новый релиз (`dsh update`).
  Если из `puppies.json` разом пропало больше половины щенков (так бывает при обрезанном файле, но и при смене помёта),
  каталог не трогается, API всё равно запускается, а `/api/v1/health` показывает проблему. Если всё верно, выполните:
  `dsh app sync-catalog --force`.
- nginx: `server-setup.sh` получает сертификат через временный HTTP-сервер (`certbot --webroot`), `deploy.sh`
  включает `deploy/nginx.conf`. Продление идёт через `/.well-known/acme-challenge/` на порту 80.
- API слушает только `127.0.0.1:8000`, база наружу не открыта. Схему меняет роль `dsh_owner`, приложение работает
  под `dsh_app` (только данные, без DDL). Пароль владельца лежит в `db.env` и в контейнер API не попадает.
  Синхронизация каталога пересоздаёт представления, поэтому её запускают от владельца: `dsh app sync-catalog`
  (`dsh app` работает через сервис `migrate`).
- Бэкапы: `deploy/backup.sh` по cron (`/etc/cron.d/domshchenkov`, 02:30 МСК; вручную — `dsh backup`). Дамп проверяется (`pg_restore -l`), шифруется age, хранится в РФ 20 дней.
  Старые копии удаляются только после успешной новой. Ошибка даёт ненулевой код, по нему cron может прислать оповещение.
- Мониторинг: внешний пинг `GET /api/v1/health`. Он отвечает 503, если уведомления застряли дольше 10 минут или упали
  за сутки. Подробности — в `GET /api/v1/admin/health`.

## Уведомления менеджерам

| Канал | Что приходит | Настройка |
|---|---|---|
| Telegram | «Новая заявка №123 · Мальтипу · Цена щенка · 14:32» + ссылка в админку. **Без имени и телефона** | `DSH_TELEGRAM_*`, чат на каждую породу — `DSH_TELEGRAM_BREED_CHATS` |
| Почта | полные данные: имя, телефон, куда писать, порода, щенок, источник | `DSH_SMTP_*` (российский провайдер), `DSH_NOTIFY_EMAILS` |
| Вебхук | `{event, id, public_id}` с подписью HMAC — для админ-панели | `DSH_WEBHOOK_URL`, `DSH_WEBHOOK_SECRET` |

Проверка до запуска: `python -m app notify-check` (на сервере `dsh app notify-check`). Покажет бота, чаты, где он
есть, с их id, доступ к заданным чатам и вход в почту. С `--send` отправит тестовое сообщение в каждый чат и письмо
каждому получателю. Токен и пароль не печатаются. Код выхода 1 — что-то не так.

Telegram — иностранный сервис. Имя и телефон в нём — трансграничная передача. Чтобы включить её:
1. Уведомить Роскомнадзор.
2. Опубликовать новую версию согласия, где передача за рубеж названа, с `"cross_border": true` в `src/data/consent.json`,
   и обновить политику.
3. Включить `DSH_TELEGRAM_INCLUDE_PD=true`. Имя и телефон придут только по заявкам, принятым под такой версией согласия.

Почта содержит полные данные. При удалении человека API возвращает `manual_steps`: какие письма удалить из ящика.
Ночная очистка до почты не дотягивается. Настройте в ящике правило: удалять уведомления старше 3 лет, лучше раньше.
Либо выключите ПД в письмах: `DSH_EMAIL_INCLUDE_PD=false`, тогда менеджер смотрит контакты в админке.

## Админ-панель

Адрес: `https://домщенков.рф/admin/`. Это резервная копия всех заявок с сайта. Заявки лежат в нашей базе, поэтому
панель работает, даже если подключённая CRM отвалится или потеряет данные.

- **Вход** — логин и пароль сотрудника: `python -m app create-admin --login olga --name "Ольга" --role manager`.
  Роль `admin` дополнительно может выгружать заявки в Excel (CSV). Выход — кнопка «Выйти» или закрыть вкладку.
- **Заявки** — вкладки-базы: «Все заявки», каждая порода, «Без породы». На вкладке: всего, открыто, новых, просрочено.
  Фильтры: статус, форма, поиск по имени, телефону или №, даты. Красная полоса слева — просрочено: новая заявка ждёт
  дольше 15 минут или прошёл срок «перезвонить». Повторный запрос того же человека не дублирует строку, а виден
  меткой «+1 повторный».
- **Карточка заявки** — кто (кнопки «Позвонить», WhatsApp, Telegram), что хотел, источник, согласие; статус,
  ответственный, «перезвонить», сумма продажи или причина отказа, комментарии; повторные и другие заявки человека;
  что смотрел на сайте; история изменений. Если двое правят одну заявку, второй увидит свежую версию, а не затрёт её.
- **Отзывы** — модерация: опубликовать, отклонить, снять по просьбе автора.
- **Сводка** — заявки по породам, формам, статусам, источникам и дням, время до первого ответа.
- **Новые заявки** — панель проверяет их раз в минуту: всплывает «Новая заявка на сайте», число новых видно в заголовке
  вкладки браузера.

Устройство: `backend/admin_ui/` — HTML, CSS и JS без сборки и без внешних библиотек. Файлы раздаёт сам API
(`/admin/`), nginx проксирует `location ^~ /admin/` туда же, куда `/api/`. Отдельный сервер и CORS не нужны.
Защита: строгий CSP (только свои скрипты и стили), данные заявок выводятся только как текст, `noindex`, токен в
`sessionStorage` (живёт до закрытия вкладки). Чтобы пускать в панель только из офиса или VPN, раскомментируйте
`allow …; deny all;` в трёх блоках `deploy/nginx.conf`: `/admin/`, `/api/v1/admin/auth/login`, `/api/v1/admin/`.
Внешней CRM тогда тоже нужен разрешённый адрес.

## API для админ-панели и CRM

Полная схема: `/api/v1/docs` (в разработке) или файл `backend/openapi.json` (`python -m app openapi`) — по нему можно
сгенерировать клиент. Вход: `POST /api/v1/admin/auth/login` → токен (12 ч, 2 ч простоя) или API-ключ для бэкенда
панели (`create-api-key`, заголовок `X-Actor` — имя сотрудника для истории).

| Метод | Что делает |
|---|---|
| `GET /admin/meta` | все статусы, виды заявок, каналы, причины отказа с русскими названиями и цветами; породы; менеджеры |
| `GET /admin/breeds` | базы пород со счётчиками: всего, открытых, новых, просроченных |
| `GET /admin/leads?breed=maltipu&status=open&assignee=me&overdue=true&q=…` | списки (`{items,total,page,per_page}`) |
| `GET /admin/leads/counts?group_by=breed,status` | цифры для вкладок и колонок канбана одним запросом |
| `GET /admin/leads/{id}` | заявка, повторные запросы, другие заявки человека, история, путь по сайту, ссылки tel/WhatsApp/Telegram |
| `PATCH /admin/leads/{id}` (+ `version` или `If-Match`) | статус, причина отказа, сумма, ответственный, порода/щенок, «перезвонить», комментарий. 409 при одновременном изменении |
| `POST /admin/leads/{id}/take` | «Взять в работу» (атомарно) |
| `POST /admin/leads` | заявка из звонка, мессенджера, Авито — в ту же базу |
| `GET /admin/puppies`, `GET /admin/puppies/{slug}/leads` | щенки со счётчиками заявок, очередь на щенка, расхождения с сайтом |
| `GET /admin/contacts`, `/contacts/{id}`, `PATCH`, `/merge`, `/erase` | люди, склейка двух номеров, удаление данных по 152-ФЗ |
| `GET /admin/reviews`, `PATCH /admin/reviews/{id}` | модерация отзывов, снятие по просьбе автора |
| `GET /admin/stats?from=…&to=…` | заявки по породам, видам, статусам, источникам, дням (по Москве), время ответа, конверсия |
| `GET /admin/export/leads.csv` | выгрузка для Excel (только роль admin, пишется в журнал) |

Ошибки всегда в одном формате: `{"error": {"code", "message", "fields": {"phone": "…"}}}`.

Для BI или прямого чтения базы есть роль `dsh_readonly` (пароль `DSH_READONLY_DB_PASSWORD` в `db.env`). Она видит
только представления `leads_*`, остальные таблицы ей недоступны (пароли менеджеров, журналы, согласия).

## 152-ФЗ: что сделано и что сделать до запуска

Сделано в коде:
- согласие — отдельный документ (`/soglasie/`, текст в `src/data/consent.json`). Хранится версия и доказательство;
- у отзывов своё согласие на обработку (`/soglasie-na-otzyv/`) и отдельное — на публикацию (`/soglasie-na-publikaciyu/`).
  Телефон автора (его требует Приказ РКН № 18) не публикуется. Снятый отзыв сразу обезличивается;
- минимизация: у посещений нет IP и строки браузера, у ссылок нет query-строки, у источника хранится только домен;
- сроки хранения (ночная очистка): контакты — 3 года с последнего обращения (открытая, но заброшенная заявка
  срок не продлевает); IP заявок — 30 дней; анонимные события — 180 дней; спам и неопубликованные отзывы — 30 дней;
  бэкапы — 20 дней;
- удаление человека по запросу с актом уничтожения: заявки обезличиваются (открытые закрываются), отзывы и
  посещения удаляются. Хеши номеров (`DSH_ERASURE_SECRET`) пишутся и в базу, и в файл вне базы (том `tombstones`).
  После восстановления бэкапа `reapply-erasures` по этому файлу повторно удаляет всех, кого стёрли позже копии;
- журнал выгрузок и просмотров без телефонов в поисковых запросах;
- шрифты раздаются со своего домена: IP посетителя не уходит в Google;
- никаких персональных данных за рубеж по умолчанию (Telegram без ПД, CI только на тестовых данных).

До первой реальной заявки:
1. Подать уведомление об обработке ПД в Роскомнадзор (ст. 22): pd.rkn.gov.ru. Указать хостинг в РФ и меры защиты.
2. Заполнить заглушки в `src/data/consent.json` (оператор, ИНН, ОГРН, адрес, почта) и в политике конфиденциальности.
   Опубликованную версию согласия не править — добавить новую и переключить `current`.
3. Назначить ответственного за обработку ПД.
4. Если в Telegram нужны имя и телефон — подать уведомление о трансграничной передаче и включить `DSH_TELEGRAM_INCLUDE_PD`.
5. Арендовать сервер в РФ, настроить бэкапы и мониторинг `/api/v1/health`.
